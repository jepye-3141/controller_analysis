## 2. Critical findings

### C1 — The "per-motor clipping" baseline does not exist in the code; the 46.4 % arm is the fully **unconstrained** dSMC — *must fix before submission*

**Paper claims.** Abstract (L82): "increases average landing site reachability from 46.4 % (per-motor clipping) to 62.9 % (saturation algorithm)". Results (L1429): "when saturation was disabled, we left the unconstrained dSMC command alone **except for the per-rotor mixer clip in order to respect the physical control constraints of the vehicle**". Table 4 column header: "Control Clipping Only" (L1464). Conclusions (L1476): "when we apply basic motor speed clipping, this breaks down".

**Code reality.** The 46.4 % column comes from the `saturation_on = false` sweep (`trajectory_optimization.m` L26–31 → logs, exact match). In that mode:
- `dsmc_constraints.m` L228–234: `u_bar = u_unc; delta_u = 0` — the raw unconstrained command is returned. No clip.
- Neither `discrete_smc_swarm_single.slx` nor `actual_discrete_smc_controller.slx` contains a single `Saturate` block (verified by enumerating every block in the archive XML).
- The plant (`system_dynamics.m`) applies `u = [T; Mx; My; Mz]` with no limiting of any kind.
- The only guard in the loop is the divergence-termination chart (`term = 1` if `norm(vel) ≥ 1e5 || norm(rotvel) ≥ 1e5`).
- Git history: no version of `dsmc_constraints.m` (or any tracked `.m`) has ever clipped the OFF path; `git log -S "clip"` finds only the s_z/s_ψ surface clip comments.

**Internal corroboration from the paper's own text.** L1431 states that under "simple clipping" the command norm "spikes above 800". Under the code's mixer, a genuinely per-rotor-clipped *applied* command satisfies `‖ū‖ ≤ 4·b·Ω²_max = 40`. A norm above 800 in the logged/plotted signal (`ctrlout` = the controller's returned `u`) is only possible if no clip was applied — which is exactly what the code does.

**Why this is critical.** The paper's central experimental claim — *naive clipping under physical constraints collapses reachability; the priority/anti-windup handler recovers it* — currently has **no supporting data point**: the "constrained without handler" condition was never simulated. What was actually measured is "handler under Ω²_max = 2 constraints (62.9 %) vs. **infinite actuator authority** (46.4 %)". That the constrained controller *beats* the unconstrained one is a genuinely interesting result (the unconstrained transients with `‖u‖ > 800` are violent and land less precisely), but it is a different scientific claim than the one in the abstract, and a reviewer who reproduces the described baseline will get different numbers.

**Remedial plan (preferred — implement the described baseline and re-run one sweep).**
1. Add a true per-rotor-clip mode to `dsmc_constraints.m`. Cleanest: replace the boolean with a 3-way mode, or add a second flag; minimal-diff version inside the existing `else` branch:
   ```matlab
   % naive per-rotor clip baseline (no anti-windup: xi stays 0)
   Om2   = TM_inv * u_unc;
   Om2   = min(max(Om2, Omega2_min), Omega2_max);
   u_bar = TM * Om2;
   delta_u = zeros(4, 1);        % baseline deliberately ignores the deficit
   ```
   `delta_u = 0` keeps `xi ≡ 0`, so the baseline is "clip, no compensation" — exactly the paper's story. (`ukm1 = u_bar` then also makes Ω_r reflect clipped speeds, consistent.)
   Wiring: `constants_struct` bus gains a `saturation_mode` field (0 = off, 1 = clip, 2 = priority) or an extra boolean; update `constants.m`, the bus creation, and `sweep_landing_centroid`'s `traj_params` plumbing.
2. Re-run the baseline arm of `trajectory_optimization.m` (~10–16 min on 12 workers) and regenerate `SAT_CMP_summary` + `TO_*_sat_off` figures.
3. Update abstract / Table 4 / conclusions numbers. Decide what TO_06's baseline trace shows: the *post-clip* norm is bounded by 40, so the ">800" sentence must either be re-pointed at the *pre-clip commanded* norm (log `u_unc` separately) or replaced.
4. Strongest presentation: keep **three** arms — unconstrained (current 46.4 % data, relabeled honestly), clipped (new), handler (62.9 %) — mirroring the envelope section, which already runs `nosat` vs `sat` and *correctly* describes `nosat` as "disregard[ing] any control constraints".

**Remedial plan (fallback — text-only).** Relabel the baseline as "unconstrained dSMC (no motor limits)" in the abstract, L1429, Table 4, and conclusions. This is honest but forfeits the paper's motivation sentence and leaves "requires a saturation handler to maintain >50 % reachability when physical control constraints are accounted for" unsupported. Not recommended alone.

### C2 — The code's mixing matrix is not the paper's `T_M`: moment rows lack the arm length `l`, and `d ≠ k_MT·b`

**Paper.** `eq:sat-mixing` (L899–907) and the prose at L909: moment rows carry `bl`; `eq:sat-TMinv`/`eq:sat-decomposition` (L937–964) carry `1/(2bl)` on the moment contributions. This is consistent with the physical mixing Eq. 1 (`eq:thrusts`, L165–180) under `T_i = b·Ω_i²`, `d = k_MT·b`, with `l = 0.2 m` and `k_MT = 0.1 m` from the nomenclature.

**Code.** `dsmc_constraints.m` L115–118 (and identically `dsmc_no_constraints.m` L52–55):

```matlab
TM = [b   b   b   b;      % b = 5
      0  -b   0   b;      % paper: 0  -bl  0  bl   (bl = 1 with b=5, l=0.2)
     -b   0   b   0;      % paper: -bl  0  bl  0
      d  -d   d  -d];     % d = 2, but k_MT·b = 0.5
```

No single `(b, d)` reconciles the two: the thrust row fixes `b = 5` (confirmed by the `|u| ≈ 40` ceiling in TO_06), which makes the paper's moment-row coefficient `bl = 1` vs. the code's `5` (**5× more roll/pitch authority per Ω²-unit in the code**) and the Eq.-1-consistent `d = 0.5` vs. the code's `2` (**4× more yaw authority**). The allocation geometry — where saturation begins, which cascade stage engages, the shape of the feasible parallelotope `U` — therefore differs materially between the documented and the implemented controller. Every saturated result in the paper (Table 4, TO figures, the Ω²_max = 2 operating point itself) was produced under the *code's* mixer. A reader reproducing from the paper with the physical values gets a much tighter moment budget and different reachability numbers.

Consistency note: the deficit-coupling matrix `D_k` is derived from the plant dynamics, not from `T_M`, so the anti-windup analysis is untouched by this finding. The Ω_r recovery (`TM_inv * ukm1`) also uses the code mixer, but is moot because `Jmp = 0` (see minor findings).

**Remedial options (author decision required).**
- **(b) Re-notate the paper to match the code — cheap, text-only, recommended for SciTech.** Present the mixer with *independent effective coefficients*: thrust coefficient `b = 5` and a moment-row coefficient (call it `b_M = 5`) and `d = 2`, stated explicitly as normalized Ω²-space implementation values for a notional actuator, *not* derived from Eq. 1 (drop or soften the "moment rows carry bl" sentence; do not add `d = k_MT b` per report-M1). All of the section's algebra (orthogonality, `T_M⁻¹`, the decomposition, `λ_max`, the cascade) is form-identical under `bl → b_M`, so this is a notation pass plus a numbers table — and it simultaneously closes report-M11.
- **(a) Physicalize the code — principled, expensive, journal version.** Set `TM = [b b b b; 0 −bl 0 bl; −bl 0 bl 0; kmt·b·(1,−1,1,−1)]` with constants from `constants.m`, then **re-tune the Ω² bounds and redo the empirical Ω²_max breakpoint study** (the current sweet-spot/breakpoint knowledge and all sweep logs assume the old mixer), then re-run both sweeps and the envelope. Budget hours, not minutes.

### C3 — The success criterion in the paper (`eq:ballistic-success`) is not what the code enforces

**Paper.** L874–881: a trial succeeds iff **for every t** in the stabilization window: (i) horizontal error ≤ 10 m, (ii) `|v_t|/|v_0| ≤ 2`, (iii) `|ω_t|/(π√3) ≤ 2`; window 30 s. The saturated-results section (L1429) states the sweep uses this same criterion.

**Code.**
- Envelope (`analysis.m` L322–346): success ⇔ sim reached the full 30 s **and** *final-time* XY within 10 m of the deploy point. No per-t position condition, no velocity-ratio condition, no rate-ratio condition.
- Sweep (`sweep_landing_centroid.m` L243–248): success (`stable`) ⇔ sim reached the full **60 s** (`sim_time = 60`, not 30 — the paper never states the sweep window) **and** *final-time* XY within 10 m of the landing target. The `vel_tol = 5 m/s` check feeds only the diagnostic `time_to_land`, not success.
- The only dynamic guard is the model's termination chart: `term = 1` if `norm(vel) ≥ 1e5 || norm(rotvel) ≥ 1e5` — three-plus orders of magnitude looser than conditions (ii)/(iii). This chart has carried the 1e5 thresholds since the initial public commit (its unused `xi` input suggests a ratio criterion may once have been drafted, but it never existed in this repo's history).

**Consequences.** A trajectory that wanders arbitrarily far and returns by the final tick counts as a success; so does one that transiently exceeds `2|v_0|` (plausible during ballistic recovery, especially near-apogee deploys where `|v_0|` is small). All reported numbers (Table 4, envelope Fig. 39) were scored under the code criterion.

**Remedial plan.** Preferred (text-only, honest): rewrite `eq:ballistic-success` to the implemented criterion — "the simulation completes the window (a divergence guard `‖v‖, ‖ω‖ < 10⁵` never trips) and the final horizontal position is within 10 m of the target; window = 30 s (envelope) / 60 s (landing sweep)". Alternative (partial post-hoc re-scoring, no re-simulation): conditions (i)-for-every-t and (ii) are recomputable from the saved per-trial `trajectory.pos/vel` in the sweep logs; **condition (iii) is not** — body rates are not logged by the sweep (only pos, vel, ctrl) — so either drop (iii) from the paper or add `rotvel` logging and re-run (~2 × 15 min). Do not leave the current text: it describes a materially stricter criterion than the one that produced the numbers.

### M1 — Stage-4 fallback returns γ = 0 (all motors off); the paper's "guaranteed" narrative and the code comment are both misleading — *confirms report F1 against code*

Behavior verified in §1/F1 above: with `Omega2_min = 0`, every stage-3 entry (paper item 4) produces `ū = 0` — a motor-cut tick in which the full `u_unc` is dumped into the auxiliary state — not a "scaled roll/pitch" command. Two additional code-side notes:

1. The comment at `dsmc_constraints.m` L312–313 ("measure-zero set of inputs in practice") is wrong. Stage 3 engages whenever `(0, Mx, My, 0)`-with-thrust-scaling fails, i.e. (code-mixer geometry, `Ω²_min = 0`) whenever commanded `T < 2·max(|Mx|,|My|)` **or** `max(|Mx|,|My|) > b·Ω²_max`. Commanded `T ≤ 0` occurs in ballistic recovery whenever the z-channel demands deceleration of a climb (`u_T ∝ −α_z·ż + g + η_z·s̃_z` goes negative for large positive `ż`), so this is a positive-measure, actually-visited regime.
2. Empirically survivable: the 62.9 % run includes these motor-cut ticks; recovery works because the next tick's `s̃` reflects the deficit through `ξ`.

**Remedial plan.** Either adopt the report-F1 *preferred* mid-band re-centering (base = `(Ω²_min+Ω²_max)/2·𝟙`, pinning collective to a fixed `T_c` and giving a *true* γ > 0 guarantee) in both code and paper — requires re-running both sweep arms — or apply the report's *minimal* fix to the paper only (state `Ω²_min = 0`, state that the closed form returns γ = 0 and the fallback is a one-tick motor cutoff, reconcile the following sentence). Fix the "measure-zero" code comment in either case. Given the SciTech timeline the minimal fix is defensible; the re-centering is the better controller and worth doing for the journal version.

### M2 — The load-bearing ±2 clip on s_z, s_ψ is absent from the paper

Both controllers clip the fully-actuated sliding variables to `[−2, 2]` before use (`dsmc_no_constraints.m` L63–68; `dsmc_constraints.m` L145–146, applied to the raw `s` *before* the `D·ξ` subtraction). The implemented reaching law is therefore `s_{k+1} = s_k − η_α Δt·sat₂(s_k)`: **constant-rate** reaching for `|s| > 2`, exponential only inside the band. The paper presents the pure exponential law (L611–615), proves Lyapunov decrease for it (L620–628), and states the control laws are "reused verbatim" in the saturated controller (L1022). Per the project record (2026-05-15 diagnostic), removing this clip lands **zero** successful sweep trajectories — it is not a cosmetic detail; it also caps the reaching-term contribution to `u_T` at `m/(cφcθ)·η_z·2`, which interacts directly with the saturation story this section tells.

Stability is not actually endangered — for `|s| ≥ 2` the clipped law gives `|s_{k+1}| < |s_k|` whenever `|s| > η_αΔt` (satisfied, since `η_αΔt ≤ 0.28 < 2`) — but the *exponential* claim does not hold globally as written.

**Remedial plan (text-only).** One short paragraph in the dSMC section: define the saturated reaching law, note the two-regime behavior (constant-rate approach, exponential once `|s_z|, |s_ψ| ≤ 2`), give the one-line `|s_{k+1}| < |s_k|` argument for the outer regime, and record the clip bound (±2) in `tab:gains-scalars`. In the saturation section, note the clip is applied to `s` before forming `s̃ = s − Dξ`.

### M3 — Two of Table 4's four metric definitions do not match the computed quantities

- **"Half-success radius (radius about the centroid containing half the successful trials)"** (caption, L1457): the code (`sweep_landing_centroid.m` L336–342) computes the radius at which the *azimuthally averaged interpolated success-ratio profile* first falls to **half its peak value** — a half-maximum (FWHM-like) radius, not a cumulative "contains half the successes" quantile. Different quantity, different number.
- **"Peak success ratio"**: the code reports the max over radial bins of that same azimuthal mean (`max(mean_ratio)`), not the max per-target ratio. This is why the table shows 0.999 rather than exactly 1 (raw per-target ratios are small-integer fractions; several equal 1.0).
- "Reachability fraction" / "integrated reachability" (L1431) / abstract "average landing site reachability": code = successful trials ÷ *attempted* trials (88/140, 65/140), where 20 of 160 grid cells are boundary-excluded (neighbor index out of range). Defensible, but the normalization and the trial counts appear nowhere in the paper.

**Remedial plan (text-only).** Rewrite the caption/paragraph definitions to what is computed: "radius at which the azimuthally averaged success ratio first falls to half its peak", "peak of the azimuthally averaged interpolated success-ratio profile", "fraction of the 140 attempted deploy×cross-track×neighbor trials that landed successfully". Alternatively re-implement the metrics to match the captions and regenerate — but the implemented definitions are reasonable; the words should move, not the code.

## 4. Minor findings (paper typos/omissions; the code is the internally consistent side)

1. **`T_y` sign typo (L712–714).** Paper defines `T_y ≜ cφ sθ sψ **+** sφ cψ`; the paper's own y-dynamics (L584) and increment usage (L737), the code (`g1_k`, both controllers), and the standard ZYX quadrotor kinematics all use `cφ sθ sψ **−** sφ cψ`. Propagates into `g_{1,k}`, hence the sign of `D_{2,1}` for anyone implementing from the paper. Fix: `+ → −`. (`T_x` at L715–717 is correct and matches code.)
2. **`f₁/f₂` sign typos (L722–732).** The definitions show `+J_r θ̇ Ω_r + K₄ l φ̇` (f₁) and `+J_r φ̇ Ω_r + K₅ l θ̇` (f₂). The paper's own discrete dynamics (L588–596) and the code (`f1_k`, `f2_k`) require `−K₄ l φ̇` (f₁, drag opposes motion) and `−J_r φ̇ Ω_r − K₅ l θ̇` (f₂). Three sign flips in the compact-definitions block; everything downstream already uses the correct versions.
3. **Gyroscopic coupling κ is dead in simulation.** Nomenclature: `κ = 0.1`; nonlinear EOM (L192–199) carries `−κ M_z ω`. The plant (`system_dynamics.m` L41–42) implements this factor as `(kwt/kmt)·Jmp = 1·0 = 0` (`Jmp = 0` in `constants.m`), so the term is identically zero in every simulation (as are the `J_r Ω_r` terms in `f₁/f₂`, consistent with "J_r ≈ 0"). State κ ≈ 0 / term-disabled for the simulated results, or set the nomenclature value accordingly.
4. **z-axis convention.** Nomenclature says NED "down positive" (L122), but the paper's own `ż` equation (L214), the linear model `ż = −v_z` (L229), and the code all treat the z *position* as altitude-up. One-word nomenclature fix.
5. **TO_06 "commanded" wording (L1431, L1443).** The logged/plotted signal (`ctrlout`) is the controller's *returned* `u = ū` — post-allocation for the saturated arm. "Commanded" reads as pre-projection. Clarify (and revisit under C1's baseline decision).
6. **Sweep protocol under-specified.** The paper never states: 60 s trial window, 8 deploy points at 20–80 % arc length, neighbor-offset targeting set {−1, 0, +1, +2}, 160-cell grid with 20 boundary exclusions → 140 trials, `reach_tol = 10 m`. One protocol sentence plus counts fixes reproducibility (partially overlaps C3/M3).
7. **Missing numerics** (report M11): add `b`, `d` (per the C2 notation decision), `Ω²_min = 0`, `Ω²_max = 2`, clip bound ±2, and `k_ξ = (0.14, 0.28, 0.28, 0.14)` to `tab:gains-scalars`.
